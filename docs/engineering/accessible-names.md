# Accessible names come from the tooltip

> Part of the kubeNimbus engineering contract, moved out of `CLAUDE.md` so it loads only when relevant. Same discipline applies: keep it current in the PR that changes what it describes.

Windows UI Automation (and so a screen reader, and `scripts/qa-ui.ps1`) asks every control for a name. A button that draws only an icon has none and reports its content's type, `Avalonia.Controls.PathIcon`; a list item whose content is a view model reports that type's name; the command palette's rows used to report a record's property dump. ENG-4 and ENG-47 recorded it, and the 0.5.1 release pass counted it: every icon button in the command bar, every sidebar row, every Applications row and every switch on the preferences page.

The rules:

1. **The tooltip is the one place the words are written.** Every icon-only control already says what it does in a tooltip, so `AutomationNames` (installed from `App.Initialize`, next to `ToolTipHitTesting`, so the screenshot harness gets it too) copies it into `AutomationProperties.Name` whenever a tooltip is set or changes, bindings included. It keeps the first clause (text after an em dash, a colon or a full stop is explanation) and drops a trailing parenthesis, which is the shortcut. A name written by hand in markup always wins: a hand-written name is a decision, a derived one is a default. A button whose content is a string, and any control with no tooltip, is left to name itself from its own text; a text box with no tooltip takes its placeholder.
2. **Do not write a second sentence for a control that has a tooltip.** Add the tooltip. A control with neither gets an `AutomationProperties.Name` (a literal for a control with no visible words, such as the switcher's `+`) or `AutomationProperties.LabeledBy` pointing at its visible label (the port-forward and replica number boxes), so the label stays the one copy.
3. **A list item names itself through its content's `ToString()`.** `ApplicationRowViewModel` overrides it ("crashloop, Degraded, demo-broken. Crash-looping (exit 1)"), and the sidebar rows bind `AutomationName` (the kind, and its API group when another kind shares the name). Computed on demand, so a row that changes in place never reads stale.
4. **The preferences cards are named from their labels.** `AutomationNames.NameCardControls` gives the switch, drop-down or number box at the right of each card the text of the label at its left, once, when the page is attached. It walks the logical tree: the page is tabs (2026-10), and only the tab on screen has visuals when the page loads, so a visual walk left the other three tabs' switches unnamed. The harness's `ux-preferences-tabs` checks a control on a tab that was not shown at load.
5. **Template parts are named by what they do**: the overlay and spinner buttons (`PART_CloseButton`, `PART_IncreaseButton`, `PART_DecreaseButton`) in one place rather than in every theme that restyles them.
6. **The dock's tabs are tabs** (ENG-54, 2026-10). They were `Border`s with a `Tapped` handler, which neither the keyboard nor UI Automation could reach. The strip is now a `ListBox` (`InspectorTabStrip`, class `dockTabs`) whose items UI Automation reads as `TabItem`s in a `Tab` (`AutomationProperties.ControlTypeOverride` on the list and, by style, on its items), named by the tab's title (`InspectorTabViewModelBase.ToString`). The selection is pushed one way from `SelectedInspectorTab` and read back in `OnInspectorTabSelectionChanged`, never bound two-way: closing the selected tab makes the list report a null selection, and a two-way binding would write that null back before `CloseInspectorTab` chose the neighbour. Each tab's close button stays inside it, named "Close <title>", and is not a Tab stop. `DockTabNameTests` pins the name.
7. **The cluster tabs are tabs too** (#236, 2026-10, the command bar's half of ENG-54). The strip in the command bar was an `ItemsControl` of `Border`s with a `Tapped` handler; only each tab's close button was reachable, and every close button was a Tab stop of its own. It is now a `ListBox` (`TabStrip`, class `clusterTabs`) read as a `Tab` of `TabItem`s named by the cluster, with the selection pattern; the selection is pushed one way from `SelectedTab` and read back in `OnClusterTabSelectionChanged`, for the dock strip's reason. The `Border.clusterTab` inside still draws hover, press and the active fill from the view model, and keeps `ElementRole="User"` (UI rule 12). The arrow keys, Home and End bring a tab to the front with focus (`OnClusterTabStripKeyDown`, a focus with a navigation method, so it draws the ring), a plain vertical wheel scrolls the row sideways (`HorizontalWheel`, #313, the same helper the dock strip uses), and a drag that moves a tab pushes the list's selection back without replacing the binding.
8. **Delete closes the focused tab, in either strip** (`CommandId.CloseFocusedTab`, sheet-only, handled by the two strips' own key handlers so a bare Delete anywhere else keeps its meaning). The close buttons are pointer targets and not Tab stops; focus moves to the tab that came to the front. A close button's name falls back to "Close tab" if its tab's title is ever null: the QA run's `<unnamed>`, disabled, offscreen close buttons fit a container that had lost its data context, and a fallback is cheaper than a ghost with no name.
9. **A sidebar section header says whether it is open.** `SidebarSectionHeader` is the `Border` it always was (`StyleKeyOverride`, so `Border.sectionHeaderRow` still styles it) with a peer of type Group and the ExpandCollapse pattern; the state is the section's `ShowKinds` (a filter force-expands a folded section, and the reader is told what is on screen), and Expand/Collapse set the section's own `IsExpanded`, the flag a click toggles.
10. **A drawn check box is a check box.** The namespace pickers draw their check rather than use a `CheckBox`, so the view model is the one writer of the state; the drawn box was not in the UIA tree at all. `CheckMark` is that `Border` with a CheckBox peer and the Toggle pattern, named by the namespace; a Toggle does what a click on the box does.
11. **A grid row is named by the row it shows and says when it is selected.** The DataGrid's row peer has neither a name nor a selection pattern, so every row read as an empty `DataItem` and a multi-row selection could only be read off the "n selected" header. `AutomationNames` names a row from its data context's `ToString()` (`ResourceRowViewModel`: name, namespace, and the cluster in a fleet list; identity only, since the name is set when the row is bound and a status in it would go stale), and `DataGridRow:selected` sets the item status to "Selected". A row type with no `ToString` of its own is left unnamed rather than named after its type: the workload, node and Helm grids' rows are among them.
12. **A menu item with a text header is named by its header.** Deriving the name from the tooltip (rule 1) made UI Automation read "Tail every pod this workload owns in one pane" for the item that says "Logs (all pods)", and the column chooser's items the same way. A `MenuItem` or tab whose header is a string is skipped by the derivation, and a header set after the tooltip clears a derived name.
13. **A toggle the view model refuses stays off through UI Automation too.** The managed-fields chip's view model sets the flag straight back over text that is not one YAML document, inside the binding's own write, and a binding does not take a value back while writing one: a click happened to come out right, a UIA Toggle left the chip pressed over the refusal (QA check M-8). `YamlEditorView` puts the chip back to what the view model kept once the write is over (`SetCurrentValue`, so the two-way binding stays). `ux-managed-fields-uia` failed before the fix with "left the chip pressed and the view model at False".
14. **A name taken from what a control shows is taken again when what it shows changes.** For a button or list item whose content is a layout and whose content type has no `ToString` of its own, `AutomationNames.NameFromContentText` names it from its first visible text blocks when it loads. A virtualizing list recycles its containers, and a recycled container is not loaded again, so after the cluster switcher's filter every row kept the name of the row first drawn in it: UI Automation reported "qa-limited" at the bounds of the row that drew `qa-cut`, and a real click there opened `qa-cut` (#367). Such a name is now marked, cleared when the content changes, and taken again once the new content is laid out. `ux-switcher-filter-uia` checks every drawn switcher row's name and bounds after a filter and after clearing it ([cluster-switcher](cluster-switcher.md)); it failed before the fix.
15. **The dock's content area is a Pane with the AutomationId `DockContent`** (#370), named "Inspector content". The QA VM crops what a dock check is about with `qa-ui.ps1 screenshot -Id DockContent`; with no id, C-9, C-10 and Y-11 of the 2026-10-13 run attached whole-window crops. It is the `ContentControl` under the dock's tab strip, so the crop is the open tab's pane without the strip or the list. A `ContentControl` is not in the control view by default (its headless peer said `IsControlElement` false, type None), and UI Automation clients work in that view (`qa-ui.ps1` walks it with `ControlViewWalker`), so it takes `AccessibilityView="Control"` and `ControlTypeOverride="Pane"` too. `ux-dock-tab-delete` finds the peer by id under the window and requires a Pane in the control view with height (red with `AccessibilityView` removed).

`AutomationPatternChecks` in the harness asserts 7–15 on headless peers (14 in `ux-switcher-filter-uia`, 15 in `ux-dock-tab-delete`): `ux-automation-patterns` (section headers' state, Expand and Collapse; grid rows' names and item status over a two-row selection; menu item names both ways round; a namespace box toggled through its pattern; the cluster strip's types, names, selection, Right and Delete), `ux-dock-tab-delete` and `ux-managed-fields-uia`; `cluster-tab-dock-many-tabs` sends a vertical wheel to the dock strip and reads the offset back (red with the handler removed).

## The keyboard walk

ENG-4's other half: a keyboard-only user has to reach every region, see where the focus is, and be able to leave wherever it went. `KeyboardChecks.KeyboardWalk` (scenario `ux-keyboard-walk`, a demo tab with two pods open in the dock) presses Tab from the command bar's first button until focus comes back to it, then Shift+Tab the same way, and fails on:

- **a trap**: 250 presses without coming back;
- **a region not reached, or reached out of order**: the command bar, the sidebar's kinds, the resource list, the dock's tabs, the open pane;
- **a stop with no focus visual**: the shared `FocusRing` in the adorner layer, a text box's own focused border, the grid's focus rectangle on its current cell, or the accent selection of a focused list's selected row (DESIGN.md rule 20). A strip (`segmented`, `dockTabs`) keeps its wash whether focused or not, so its items draw the ring, and so do the sidebar's rows, which sit in an `ItemsControl` rather than a list;
- **a list spread over many stops**: the sidebar's catalog is one stop (`TabNavigation="Once"`), entered on the selected kind; the arrow keys, Home and End move inside it, Enter or Space opens a kind or folds a section, Left and Right fold and unfold. A log pane is one stop too, the list itself with the ring around it (styles on `ItemsControl#LogItems` in `Theme.axaml`), where each `SelectableTextBlock` line and each JSON line's expander used to be one; nothing inside a row is a stop. Not a line as the single stop: the list virtualizes, so the line Tab last landed on could be recycled under a new log line and leave focus on a hidden line with no ring, which the walk caught in about one run in three before the demo's log timer was waited for and the list made the stop. Before this pass a walk from the command bar crossed every sidebar row (35 to over 100) and every visible log line, and the section headers were not reachable at all; it is about 30 stops now.

It then presses the arrow keys in the dock's strip (the next tab comes to the front) and in the sidebar. `KeyboardChecks.LeaveEditorKeys` (`ux-leave-yaml-editor`, `ux-leave-exec-terminal`) checks the way out of the two controls that keep Tab: the YAML editor indents with it and the exec terminal sends it to the shell, so Ctrl+Tab and Ctrl+Shift+Tab (`CommandId.LeaveEditor`, handled in `ClusterTabView.OnLeaveEditorKeyDown`) move to the next and previous stop outside them, and reach neither the text nor the pod. Each part was confirmed red against the code without it.

What the walk does not cover, stated: the cluster tabs are one stop inside the command bar's region, which the walk passes without naming it (their keys are `ux-automation-patterns`'), selecting or copying one log line and opening a JSON line from the keyboard (the pane's Copy copies the visible lines; selection and the expander are pointer gestures), the Applications mode, overlays other than the palette's own focus handling (`ux-overlay-focus`), and anything a real screen reader announces, which only a run of Narrator or NVDA on the release build shows.

`AutomationChecks` in the screenshot harness walks the automation peers of every scenario's window the way a UI Automation client does. It fails the run on any peer that throws, and on any operable control (button, item, edit, drop-down, switch) whose name is empty or a type name, so a new icon button with no tooltip and no name fails the render step the day it is added. It is a check on the names the app sets, not on what the Windows provider reports: a headless peer is not that provider, and a name that looks fine there can still come back empty from UIA, which is why the check that counts for a release is `scripts/qa-ui.ps1 dump` against a real build, with `<unnamed>` as what to look for. The 0.5.1 pass did that on the NativeAOT build for the command bar, the sidebar (Argo, Helm and both Widget rows included), the Applications rows, the dock tabs and the palette.

What is not covered, stated: the inner text box of a number box (a template part of a control that is itself named, skipped by the check), the DataGrid's cells, a selection pattern on its rows (the item status stands in for it; a real pattern needs a row peer the grid does not let the app replace), the YAML editor, which AvaloniaEdit exposes with no Edit type and no Value pattern (a peer would need a subclass of its text area), the ☰ menu's items being invokable through UIA (#236's earlier note, not reproduced headless), and the duplicate name `Close` shared by the window's caption button and the action strip's Close button, which made a name-based QA script close the app.
